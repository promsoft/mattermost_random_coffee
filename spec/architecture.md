# Random Coffee Bot — архитектура

Документ соответствует реализации этапов 0–4 ([план](plan.md)).

## Стек

- **Python 3.12+**, асинхронный рантайм (`asyncio`)
- **mattermostdriver** — REST API + WebSocket-клиент Mattermost
  (WebSocket — через наш `ClientTLSWebsocket`: фикс серверного SSL-контекста драйвера)
- **FastAPI + uvicorn** — HTTP-эндпоинт callback'ов кнопок (`POST /actions/{secret}`)
- **APScheduler** — cron-задачи (пн/ср/вс по Europe/Moscow)
- **SQLite + SQLAlchemy 2.x** (sync-движок: на старте десятки активных участников, SQLite спокойно тянет и тысячи) + **Alembic** для миграций
- **pydantic-settings** — конфиг из env / `.env`
- **Docker + docker compose** — деплой на хосте Mattermost; образ на
  `python:3.12-alpine` (0 CVE), еженедельная пересборка в CI — см. [security.md](security.md)
- **pytest** — тесты (домен тестируется через `FakeGateway`, без сети); **ruff** — линтер

## Компоненты

```
┌─────────────────────────── bot (один процесс) ───────────────────────────┐
│                                                                           │
│  WebSocket listener ──┐                                                   │
│  (DM-сообщения,       │      ┌──────────────┐      ┌──────────────────┐   │
│   текстовые команды)  ├────▶ │ Command       │ ───▶ │ Domain services  │   │
│                       │      │ router        │      │  - Registration  │   │
│  HTTP server ─────────┘      └──────────────┘      │  - Matching      │   │
│  (POST /actions —                                  │  - MeetingFlow   │   │
│   кнопки interactive                               │  - Rating        │   │
│   message attachments)                             │  - Admin         │   │
│                                                    │  - Complaints    │   │
│  APScheduler ────────────────────────────────────▶ └────────┬─────────┘   │
│  (пн 07:00 пары, ср 14:00 статус, вс 14:00 оценки)          │             │
│                                                             ▼             │
│                                              SQLite (volume /data)        │
│                                                             │             │
│  Mattermost REST API ◀──────────────────────────────────────┘             │
│  (отправка DM, посты в канал анонсов)                                     │
└───────────────────────────────────────────────────────────────────────────┘
```

Один процесс, один контейнер. WebSocket — приём текстовых команд в DM; HTTP-сервер — приём
нажатий кнопок (Mattermost шлёт POST на URL интеграции `/actions/{ACTIONS_SECRET}`; на Free
Edition интерактивные кнопки в message attachments работают, нужен только URL, достижимый
с сервера Mattermost — рекомендуемый способ: общая docker-сеть, `http://coffeebot:9000`).

## Модель данных

```sql
users (
  id INTEGER PK,
  mm_user_id TEXT UNIQUE NOT NULL,      -- ID пользователя в Mattermost
  username TEXT NOT NULL,
  profile TEXT,                          -- свободный текст: telegram, whatsapp, о себе;
                                         -- ≤500 символов, санитизируется (см. security.md)
  state TEXT NOT NULL,                   -- active | paused | paused_by_admin | paused_by_complaint
  unmatched_streak INTEGER DEFAULT 0,    -- сколько недель подряд без пары (приоритет матчинга)
  awaiting_profile BOOLEAN DEFAULT 0,    -- следующее сообщение сохраняется как профиль
  created_at, updated_at
)

meetings (
  id INTEGER PK,
  week_start DATE NOT NULL,              -- понедельник недели встречи
  user1_id, user2_id → users.id,
  status TEXT NOT NULL,
  -- scheduled        : пара собрана, уведомления отправлены
  -- declined         : один из участников отказался от этой пары
  -- postpone_pending : один предложил перенос, ждём ответа второго
  -- postponed        : перенос принят → создаётся новая meeting на week_start+7
  -- cancelled        : отменена (участником в опросах / админом / при отказе от переноса)
  -- completed        : созвон состоялся (по итоговому опросу)
  -- no_response      : неделя кончилась, итог не получен
  midweek_status_u1 TEXT, midweek_status_u2 TEXT,  -- agreed | called | cancelled | no_contact
  rating_u1 INTEGER, rating_u2 INTEGER,            -- 0..5, оценка, поставленная этим участником
  postponed_from_id → meetings.id,       -- если встреча создана переносом
  postpone_by_id → users.id,             -- кто предложил перенос (отвечает только второй)
  cancelled_by TEXT,                     -- user | admin
  notified_at DATETIME,                  -- когда отправлена карточка пары (идемпотентность)
  midweek_sent_at DATETIME,              -- когда отправлен опрос среды
  survey_sent_at DATETIME,               -- когда отправлен итоговый опрос
  created_at, updated_at
)

complaints (
  id INTEGER PK,
  meeting_id → meetings.id,
  reporter_id, accused_id → users.id,
  status TEXT NOT NULL,                  -- open | resolved
  created_at, resolved_at
)
-- текст жалобы сознательно не собираем: подробности админ выясняет в личке
```

- **Рейтинг** не хранится отдельно: `rating(user) = SUM(оценок, полученных user)` по
  `completed`-встречам — считается запросом (даже на сотнях участников это копейки). Кэшировать не нужно.
- **Кулдаун пар**: пара (A, B) допустима, если нет meeting с этой парой (в любом порядке)
  с `week_start > today - 365 дней` — независимо от статуса (по спеке п. 9).

## Алгоритм матчинга (пн 07:00 МСК)

1. Берём всех `users.state = active`.
2. Сортируем: сначала по `unmatched_streak` (убыв.) — приоритет тем, кто остался без пары,
   затем по рейтингу (убыв.) — спека п. 8.
3. Жадно: берём первого без пары, ищем в остатке самого верхнего совместимого
   (не встречались за 365 дней). Нашли — пара; нет — кандидат уходит в пул свободных.
4. «Лишний» при нечётном числе остаётся в пуле свободных, `unmatched_streak += 1`;
   у получивших пару streak сбрасывается.
5. Перед матчингом встречи прошлых недель без итога закрываются как `no_response`.
6. Идемпотентность матчинга — по «регулярным» встречам недели (`postponed_from_id IS NULL`):
   встреча, перенесённая с прошлой недели, не считается выполненным матчингом, но её
   участники исключаются из нового подбора (они уже заняты).
7. Пул свободных живёт всю неделю: отказ от пары (`declined`) и регистрация/возобновление
   участников среди недели → попытка домэтчить из пула немедленно (если матчинг недели уже был).
   «Занятыми» считаются участники со встречей `scheduled`/`postpone_pending` на эту или
   будущую неделю либо `completed` на этой.

## Жизненный цикл встречи

```
scheduled ──ср 14:00 опрос──▶ (статусы участников записываются;
   │                           ответ «отменили» ──▶ cancelled)
   ├─ «отказаться от пары» ──▶ declined ──▶ оба в пул свободных, немедленный домэтч
   ├─ «перенести» ──▶ postpone_pending ──▶ второй (не инициатор):
   │       ├─ принял  ──▶ postponed + новая meeting на след. неделю (пара та же)
   │       └─ отказал ──▶ cancelled (встреча несостоявшаяся)
   ├─ админ отменил («админ отменить <id>») ──▶ cancelled (cancelled_by = admin)
   └─ вс 14:00 итоговый опрос: «состоялась?» + оценка 0–5
           ├─ хотя бы один ответил «да» ──▶ completed (+ оценки в рейтинг;
           │                                «да» приоритетнее «нет»)
           ├─ «не состоялась»            ──▶ cancelled
           └─ никто не ответил           ──▶ no_response (при след. матчинге)
```

Жалоба: команда `пожаловаться` в DM → бот показывает партнёра текущей недели и просит
подтверждения кнопкой → `accused.state = paused_by_complaint`, уведомление всем админам
в DM; разблокировка — только `админ снять-паузу` (закрывает открытые жалобы).

## Интерфейс

### Участник (DM с ботом)

- Кнопки меню (набор зависит от состояния): **Зарегистрироваться · Пауза ·
  Возобновить · Изменить профиль**
- Профиль: бот просит одним сообщением прислать контакты/о себе (свободный текст,
  ≤500 символов; сохраняется следующее сообщение после регистрации/кнопки, либо
  сразу командой `профиль <текст>`).
- Карточка пары (пн): групповой канал (бот + оба участника), профили обоих.
  Кнопки **Отказаться от пары · Перенести на след. неделю**. Отказ → встреча `declined`,
  оба в пул, немедленный домэтч; перенос → запрос второму участнику с кнопками
  **Согласиться на перенос · Отменить встречу**.
- Опрос среды: кнопки **Договорились · Уже созвонились · Отменили · Ещё не связывались**
- Опрос воскресенья: **Да, состоялась / Нет, не состоялась**, затем оценка **0–5** (кнопки)
- Жалоба: команда `пожаловаться` → подтверждение кнопкой
- Текстовые команды: `помощь`, `регистрация`, `пауза`, `возобновить`, `профиль`,
  `пожаловаться` (+ английские синонимы)

### Админ (DM, доступ по списку username'ов в конфиге)

- `админ встречи` — встречи текущей недели со статусами, ответами среды и оценками
- `админ участники` — участники с состоянием, рейтингом и streak'ом
- `админ жалобы` — открытые жалобы
- `админ отменить <meeting_id>` — участники уведомляются
- `админ пауза <username>` / `админ снять-паузу <username>` (снятие закрывает жалобы)

### Канал анонсов

- Пн после матчинга: «Неделя стартовала, собрано N пар, M в пуле. Хочешь участвовать — напиши боту»
- (пост-MVP) итоги недели/статистика

## Конфигурация (env)

`MM_URL`, `MM_BOT_TOKEN`, `ANNOUNCE_CHANNEL_ID`, `ADMIN_USERNAMES`, `TZ=Europe/Moscow`,
`MATCH_WEEKDAY/HOUR/MINUTE` (пн 07:00), `MIDWEEK_WEEKDAY/HOUR/MINUTE` (ср 14:00),
`SURVEY_WEEKDAY/HOUR/MINUTE` (вс 14:00), `DB_PATH=/data/coffee.db`,
`ACTIONS_BASE_URL` + `ACTIONS_SECRET` (URL и обязательный секрет эндпоинта кнопок),
`HTTP_HOST/HTTP_PORT` (где слушает эндпоинт), `HTTP_PUBLISH_PORT` (хост-порт в compose),
`LOG_LEVEL`. Полная таблица — в README.

## Надёжность

- Все рассылки идемпотентны: матчинг — раз в неделю по `week_start`; карточки пар,
  опросы среды и воскресенья — по `notified_at`/`midweek_sent_at`/`survey_sent_at`
  с коммитом по одной встрече. Рестарт посреди рассылки не дублирует сообщения.
- При старте — догон пропущенных задач этой недели (все идемпотентны). Догон матчинга
  ограничен 72 часами от планового времени: в конце недели пары не собираем,
  опоздавшие ждут понедельника; опросы догоняются без ограничения (внутри недели).
- Ответы кнопок обрабатываются по `meeting_id` + `user_id` из server-side контекста
  action'а — повторные нажатия безопасны, чужая встреча отклоняется.
- Рассылки отправляются последовательно (один процесс) — десяткам участников хватает;
  при росте до сотен добавить паузу между отправками (rate limits API Mattermost).
