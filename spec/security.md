# Random Coffee Bot — соображения по безопасности

Зафиксированные решения и наблюдения. Контекст: бот работает на одном хосте
с сервером Mattermost (Free Edition — без подписи интеграционных запросов),
код и Docker-образ публичны.

## Границы доверия

```
[участники] ──клики/сообщения──▶ [сервер Mattermost] ──REST/WS + callbacks──▶ [бот] ──▶ [SQLite]
```

- **Участникам не доверяем**: всё, что они контролируют, — это текст сообщений
  боту и факт нажатия кнопки. Идентичность участника всегда берём из данных
  сервера Mattermost, никогда из содержимого сообщений.
- **Серверу Mattermost доверяем**: он хранит токен бота и секрет кнопок,
  его админ по определению внутри границы доверия.
- **Хосту доверяем**: root на хосте видит трафик бот↔MM, файл БД и `.env`.
  Отдельной защиты от него нет и не планируется.
- Безопасность не строится на скрытности кода (принцип Керкгоффса):
  публичность репозитория и образа не ослабляет ни один из рубежей ниже.

## Аутентификация callback'ов кнопок

Mattermost Free **не подписывает** POST-запросы интеграций (нет HMAC/токена
из коробки). Принятая схема:

1. **Секрет в URL** (`ACTIONS_SECRET`, обязателен — бот не стартует без него):
   кнопки создаёт бот, зашивая `{ACTIONS_BASE_URL}/actions/{ACTIONS_SECRET}`
   в `integration.url`. Сравнение секрета — `hmac.compare_digest` (константное
   время, без утечки по таймингу).
2. **Mattermost не раскрывает URL/context клиентам**: перед отдачей поста
   клиентам сервер вырезает интеграционные данные действий
   (`StripActionIntegrations` в `PreparePostForClient`); клиент видит только
   id и подпись кнопки. Клик — это `POST /api/v4/posts/{post_id}/actions/{action_id}`
   к серверу MM, и уже сервер сам вызывает URL интеграции, добавляя `user_id`
   нажавшего. Это документированное свойство: в context/URL можно класть
   секреты, участники их не увидят.
   <https://developers.mattermost.com/integrate/plugins/interactive-messages/>
3. **Сетевая изоляция — второй рубеж**: эндпоинт слушает только внутренний
   интерфейс (`HTTP_HOST=127.0.0.1`; в docker compose порт проброшен только на
   `127.0.0.1` хоста). Даже при утечке секрета снаружи запрос не доставить.
4. **Идентичность нажавшего** — поле `user_id` в payload, его проставляет
   сервер MM; клиент подменить его не может. Бот доверяет `user_id`, потому
   что запрос пришёл с правильным секретом по внутренней сети.

Итого: секрет — общий ключ бот↔сервер MM (аналог webhook-токена). Узнать его
могут только админ сервера MM (он и так владеет токеном бота) и root хоста.

## TLS

- В `mattermostdriver` 7.3.2 баг: WebSocket создавался с **серверным**
  SSL-контекстом (`Purpose.CLIENT_AUTH`); современный Python такое соединение
  отвергает. Исправлено в `coffeebot/mm_websocket.py` (`ClientTLSWebsocket`).
- Верификация сертификата сервера **всегда включена** — в отличие от
  оригинального драйвера, возможность её отключить убрана сознательно.
  Для self-signed сертификатов — добавить CA в системное хранилище доверия,
  а не отключать проверку.

## Секреты и конфигурация

| Секрет | Где живёт | Куда не попадает |
|---|---|---|
| `MM_BOT_TOKEN` | `.env` на сервере | git (`.gitignore`), Docker-образ |
| `ACTIONS_SECRET` | `.env` на сервере | git, образ, клиенты MM (см. выше) |
| `DOCKERHUB_TOKEN` | GitHub Actions secrets | логи CI (маскируется) |

- `.env` в `.gitignore`; в репозитории только `.env.example` с пустыми значениями.
- Генерация секрета: `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
- Ротация при подозрении на утечку: заменить `ACTIONS_SECRET` в `.env` и
  перезапустить бота (старые кнопки в уже отправленных постах перестанут
  работать — это приемлемо); токен бота перевыпускается в System Console.

## Публичность Docker-образа и кода

Проверено перед публикацией (см. Dockerfile):

- В образ копируются только `requirements.txt`, `pyproject.toml`, `alembic.ini`,
  `alembic/`, `src/` — ни `.env`, ни БД, ни истории git.
- В build-истории образа секретов нет (секреты не передаются как build args).
- Адрес продакшен-сервера в коде не зашит (только в `.env`).
- Знание кода не помогает атакующему: схема `/actions/{secret}` защищена
  самим секретом и внутренней сетью, а не скрытностью.

Вывод: публичные образ и репозиторий безопасны. Единственное последствие —
код становится открытым, это осознанное решение (лицензия MIT).

## CI/CD (GitHub Actions)

- Имя образа захардкожено в workflow — PR не может перенаправить публикацию.
- Job `docker` выполняется только на `push` в `main`/теги (`if: github.event_name == 'push'`);
  для PR из форков секреты GitHub и так недоступны.
- В workflow нет интерполяции недоверенного ввода (заголовков PR, сообщений
  коммитов и т.п.) в `run:`-команды — вектор command injection отсутствует.
- `DOCKERHUB_TOKEN` — access token с правами Read/Write (не пароль аккаунта).

## Данные участников

- Профиль — свободный текст с контактами (telegram, whatsapp, ...): это
  персональные данные, участник делится ими добровольно и показываются они
  только его паре (в групповом канале пары).
- Хранение: SQLite в Docker volume на том же хосте, что и сам Mattermost —
  новых мест хранения ПД не появляется. Бэкапы файла БД наследуют ту же
  чувствительность, что и сам файл.
- История встреч хранится бессрочно (требование спеки п. 6).

## Известные ограничения и осознанные допущения

- **Нет rate limiting на эндпоинте кнопок** — приемлемо: эндпоинт доступен
  только с хоста; источник запросов — сервер MM.
- **Секрет один на всех** (не per-user): компрометация требует доступа к
  серверу MM или хосту, где есть и более ценные цели; per-user токены не
  оправдывают сложности на этом масштабе.
- **DM-команды без подтверждения**: `пауза`/`регистрация` от имени участника
  шлёт сам Mattermost (WebSocket-событие с `user_id` отправителя) — подмена
  невозможна без компрометации аккаунта участника; этот риск вне зоны бота.
- Жалобы (этап 4) позволят участнику заблокировать партнёра до разбора
  админом — возможен абьюз самой жалобы; митигируется тем, что жалобы видны
  админам и разблокировка в их руках (антиспам-меры — по результатам
  эксплуатации, см. backlog).
